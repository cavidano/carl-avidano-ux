# Application sites

## Current direction

Every application uses the same approved case studies as the main site. Carl’s agreed workflow is a custom landing page and relevant project selection per application, without separate case-study copies. The October 1 correction removes the duplicated MDX and connects all routes to `src/content/portfolio/`. Complete cards, headings, descriptions, images, captions, and results update together on the next publish. The same rule applies to every Drawing Board article and to new published articles. The custom employer introduction, Who I am, and What I do remain in the application landing page’s `site.json`. `src/sites/<application>/projects.json` contains only the ordered `featured` slug list. Publication state, employer introduction, About copy, article selection, and résumé remain independent.

## Start an application

1. Confirm the employer, exact role, requisition, and official posting. Read the entire posting and assess it as a whole before recommending the role or beginning production, following the [evidence guide](application-tailoring-evidence-guide.md). Include qualifications, employer flexibility, location/pay conditions, and application instructions; report any inaccessible sections. Once proceeding is justified, create a new `codex/<application>-microsite` branch from the appropriate current base. Preserve existing uncommitted work before switching branches.
2. Choose a unique lowercase URL slug, such as `employer-role`. Add `{ id: 'employer-role', status: 'draft' }` to `applications` in `src/lib/application-sites.js`.
3. Create `src/sites/<application>/` and `public/<application>/`. Required source files are `site.json`, `Hero.astro`, `projects.json`, `articles.json`, `README.md`, and `application-brief.md`. Add `pages/about.mdx` only when that application needs its own About copy; otherwise its route renders the main `src/pages/about.astro` directly with application-scoped links. The public directory needs its independent `resume-carl-avidano.pdf`.
4. Reuse the main case studies directly; do not copy their MDX or rewrite their narratives. Use an existing application’s folder structure as a structural example, then tailor the landing page to the verified role and choose its featured project slugs in `projects.json`. Do not inherit another employer’s positioning, job records, publication claims, or résumé.
5. Use the official employer SVG logo, record its source, and verify the light, dark, and forced-colors treatments. Keep decorative artwork in that site's `images/` folder and set `backgroundImage` in `site.json` to its relative path, such as `images/skyline.png`. Compose `Hero.astro` with `src/components/Applications/ApplicationHero.astro`. Shared introduction and background styles live in `Applications/style.scss`. Each employer keeps its own image; all images use the same 2:1 format, top crop, opacity, and fade. Astro generates 640×320, 1280×640, 1920×960, and 2000×1000 WebP variants without changing the originals. Prepare future artwork at 2000×1000 or larger in that ratio.
6. Before tailoring copy, assess fit and create `job-evidence-map.md` using the [application tailoring evidence guide](application-tailoring-evidence-guide.md) alongside the [Jared Spool reference](jared-spool-ux-portfolio-2026.md). Map every substantive responsibility and qualification to verified evidence, the exact site or résumé placement, and any gap. Read current Confluence sources, the official job description, the actual résumé, and Carl's latest instructions. Distinguish system ownership from management of a system team; do not use copy to disguise a missing requirement. Select projects for their distinct evidence, without an automatic three-project limit. Keep their order in the `projects.json` → `featured` array. The application homepage's Drawing Board selection uses the ordered `articles.json` → `featured` array of shared source filenames without `.mdx`; its full listing retains all published articles.
7. Record document work in `application-documents.md`. Follow the Avidano job application skill for the separate InDesign source and PDF exports under `/Users/carlavidano/Projects/Job Applications/CVs/<application>/`. If a general résumé is temporarily copied for preview, label it as such in the records.

The build validates the registry, required files, homepage fields, and independent résumé path. Registration does not approve content or check the résumé's factual suitability.

## Shared content and application-specific copy

- Application writing lives under [Custom Applications](https://avidanodigital-team.atlassian.net/wiki/spaces/CAU/pages/28442625) in CAU, with one editable page per employer. These pages hold the landing and About copy, project selection, references to the shared main case studies, and a separate editorial evidence table. Edit each case study on its main Confluence page, never in a duplicate application narrative. Read the current page before editing and synchronize approved revisions with that application's local sources. Record its URL and verification date in `copy-review.md`. Main-site Case Studies and Drawing Board writing stays in its existing collections.
- The application landing page uses a short greeting and role connection, followed by a single introduction beneath “Curated case studies.” Use the same complete card as the main site: project name, shared headline, current description, image, theme, and button. Card content is never overridden per application. Use the current shared case-study descriptions. Tailor the application introduction and project selection; revisions must stay within Carl’s requested scope. Preserve the “Who I am” and “What I do” section after the case studies, with its About Me button directly beneath the two columns. The Drawing Board follows that section. Copy revisions do not authorize removing sections, relocating buttons, or reducing featured articles.
- Keep layout changes in `src/components/` and `src/layouts/`. Applications use the same `GlobalHeader`, `NavigationLinks`, Natura11y flyout, and page components.
- Put components used specifically by applicant sites in `src/components/Applications/`, with their styling in SCSS. Keep components used by the main portfolio too, such as `GlobalHeader` and shared page templates, in their existing shared folders.
- Use `SiteLink` and unscoped internal links such as `/about`, `/case-studies/phoenix`, and `/resume-carl-avidano.pdf`. MDX anchor links are mapped through `SiteLink`. Application case-study list links resolve to that application's `#projects` section.
- Do not add employer-specific branches to shared page components. Place copy in `site.json` or MDX, logo choices in `Hero.astro`, decorative artwork in `site.json` → `backgroundImage`, and the common background treatment in `Applications/style.scss`.
- Keep each application’s landing/About copy and résumé independently editable. Case-study text and images remain shared. Application-specific hero artwork uses distinct files.
- Keep drafts, approvals, exports, publication, and submission as separate facts in the working records. Existing records contain history; use the latest verified status.

The introduction is a normal-flow flex layout. `Layout.astro` renders `ApplicationBackground.astro` only on each application’s landing page. All interior pages omit both the decorative layer and its image stylesheet. It uses a viewport-height frame and downward fade at 20% opacity, positioned at the top of the document. It scrolls with the page. Keep the shared header inside its existing introduction wrapper so the flex layout does not change its width. The top gradient belongs to `GlobalHeader` and its SCSS, so every application page has the same header surface; do not add a second gradient to the landing page. `Layout.astro` loads each application's generated `background.css`; that endpoint uses Astro to produce responsive WebP assets. No decorative `<img>` or inline image styles are needed. Logos remain semantic images, and forced-colors mode hides the artwork. Every case-study page uses the same composition: its project color extends behind the navigation and entire marquee header. No application-specific header or result treatment is allowed.

## Review and launch

Use `npm run dev` for ongoing work. Run `npm run build:review` and `npm run preview:review` for a static review of the main site and all applications. This output goes to `dist-review/` and must stay local.

Before launch, review the homepage, About page, project order, responsive layout, mobile navigation, light/dark themes, forced colors, and résumé download. Verify the final exported résumé against its website asset, including visible and embedded portfolio links. Link checks cannot establish that a PDF is the correct approved document.

When Carl requests publication, change only that application's registry status to `published`, run `npm run build`, and review the resulting production output. The build compares each application’s case-study header, body, figures, and description with the main version, allowing only scoped internal links. It also checks internal links, referenced assets and responsive image candidates, required application pages, canonical URLs, article schema, sitemap exclusion, and navigation isolation. Draft application directories must be absent from `dist/`, including their static assets.

Commit and publish through the existing Cloudways process only with the requested publication scope. Verify the live pages and résumé after deployment, then record the result. Submitting the job application is a separate action.

## Maintenance boundaries

The framework configuration uses one shared route for every application. It has no dependency on BNY's component type or a fixed employer count. New IDs are checked for reserved routes and duplicates.

The production and review builds use the same source and locked dependencies. The `APPLICATION_PREVIEW=true` setting is confined to the review build command; production link checks reject draft application directories even if that setting was accidentally inherited.

## Rejected applications

When Carl confirms a rejection, remove that applicant site from the project. Delete its `src/sites/<application>/` and `public/<application>/` directories, any older standalone page route, and unused employer-specific images and site working notes. Preserve shared case studies, shared components/media, and the separate InDesign/PDF application archive. Git history retains the removed website work.

Remove its entry from `applications` and add its slug to `retiredApplicationSites` in `src/lib/application-sites.js`. The build rejects retired source directories and routes, verifies that they are absent from the output, and writes `.retired-applications.json` into the deployment artifact. The Cloudways workflow excludes that manifest from public uploads and removes only its validated, explicitly listed application directories after deployment. Active build directories and shared routes cannot be removal targets. Keep the retired slug in the list to prevent accidental reuse.

Run both builds before committing. After the next authorized deployment, verify the old route no longer serves the applicant site. Local commits do not remove live content by themselves. Deployment synchronizes the generated case-study and Drawing Board directories for main and built applications, removing stale renamed or unpublished pages within those directories only.
