### Reproducible measurements

Source scope is Core `src/scss/**/*.scss`, `src/js/**/*.js`, and `src/index.js`; Bootstrap `scss/**/*.scss`, `js/src/**/*.js`, and its two JS entry points. Counted each file once. | Measurement | Core 5.2.6 | Bootstrap 5.3.8 | Interpretation |
| --- | ---: | ---: | --- |
| Sass source | 179,684 bytes / 44 files | 328,410 bytes / 92 files | Core has 45.3% fewer source bytes |
| JavaScript source | 96,864 bytes / 19 files | 141,561 bytes / 28 files | Core has 31.6% fewer source bytes |

Uncompressed minified CSS is 265,266 versus 232,111 bytes; JS is 41,638 versus 60,539 bytes, or 80,496 for Bootstrap with Popper. Core is not smaller in every delivery measure. Full uncompressed CSS + JS without Popper is larger for Core. Do not use npm unpacked package size or node_modules as website payload.

### Maintenance findings and boundaries

- Core declares no runtime dependencies, peer dependencies, or optional dependencies; its JS imports inspected here are internal. Bootstrap declares Popper as a peer dependency for dropdowns, tooltips, and popovers. Bootstrap 5 does not require jQuery. Core still has build dependencies, and maintaining its own behavior remains an obligation.
- Core centralizes overlay behavior, focus handling, keyboard navigation, and delegated events. Its React package reuses Core CSS and focus utilities while owning React behavior. These are concrete ways to avoid maintaining separate copies. Bootstrap also has shared utilities; reuse is not unique to Natura11y.
- Both systems support Sass customization, and Bootstrap documents individual JS imports. A full-distribution comparison does not predict a tailored application's size. Core's default entry point initializes its component collection, while its public exports expose the bundle and selected utilities rather than individual component modules; modular JS packaging is a possible future improvement, not work started by this audit.
- Component sets differ: Bootstrap includes tooltip, popover, toast, scrollspy, and positioning behavior; Core includes its own lightbox, form, table, navigation, and track patterns. This audit does not claim feature or accessibility parity, compare security quality, or measure unused CSS on a real site.
- Source size and dependency count describe code surface. They do not measure technical debt, maintenance hours, defects, or how much customization a particular project needs. A smaller self-owned system also carries ongoing testing, compatibility, accessibility, and release responsibilities. The supported story is Carl's deliberate effort to keep his foundation understandable, limit dependency coupling, and share behavior across implementations. A percentage claim about reduced technical debt would require project-specific before/after evidence.

## Nielsen Norman Group portfolio reference

On September 28, 2026, Carl asked to retain [5 Steps to Creating a UX-Design Portfolio](https://www.nngroup.com/articles/ux-design-portfolios/) by Rachel Krause, published August 4, 2019. He particularly values its case-study structure. The article was read directly on September 28. The guidance below is a paraphrased reference, not a reproduction of the article.

### Article guidance

Make relevant strengths easy for hiring readers to recognize. Show reasoning, collaboration, and intermediate work alongside final designs. Project selection also considers interesting stories, what differentiates the designer, where they brought value, and what they learned. Select projects for the work you want to do; the suggested three-to-five projects is guidance, not a rigid limit. Use a consistent, scannable presentation, respect confidentiality, and improve the portfolio through reader feedback. When time is limited, deepen one or two substantial projects.

### Seven-part case-study checklist

1. **Problem or hypothesis:** What needed solving, or what proposition did the work investigate?
2. **Contribution and collaboration:** What did you own, and how did you work with others?
3. **Reasoning:** What evidence and decisions led to the approach?
4. **Effectiveness:** What shows whether the solution addressed the problem?
5. **Constraints and alternatives:** What obstacles or rejected approaches shaped the work?
6. **Impact:** What changed for users and the organization?
7. **Learning:** What did the experience teach you?
